# 记忆召回隔离检查 V0.1

日期：2026-11-08。执行者：Codex 主agent（/root），无委派。

任务：用户要求优先检查记忆召回是否有效。本次测试不以“学习模块整体不完整”作为预设结论，而是分别检查内容有没有存下、能否找回、是否进入模型输入、模型能否使用。正式实例继续锁定，不改变实际选择，不执行模型候选行动，保留旧证据。

## 测试范围

业务代码保持本次任务开始时的行为，仅新增：

- `evaluation/memory_recall_probe.py`：新隔离实例中的召回检查与能力探针。
- `scripts/run_memory_recall_probe.py`：冻结源码、运行检查、显式小规模Codex对照、保存证据、结束时停止并加锁。
- `tests/test_memory_recall_probe.py`：运行器正常流程、格式失败保留输出与用量、离线不构造模型三个模拟测试。

真实对照使用现有 `config/local/codex.json`。每次是独立会话，无工具执行、无续接、无自动重试。普通思考路径的 `Engine.prepare → Memory.retrieve → selected_memories` 已有记忆正文输入；它与此前只含统计及版本引用的认知经验快照不同。

先做11项基础检查：旧英文标识、中文匹配、只取最新修订、访问权限、已删除排除、当前输入不冒充旧记忆、模型生成来源标识、重启后持久化、新对话输入记忆正文、不同实例隔离、工具结果引用自动记忆。另设三个能力探针，单独报告：同义改写、无关问题返回空、工具观察正文召回。不能用基础项通过掩盖这些缺口。

真实Codex对照三道题、每题两个条件，共6次：

| 问题 | 记忆来源 | 检查目标 |
| --- | --- | --- |
| 当前有效取件码 | 用户文字自动编码，随后有明确修订 | 能否使用最新版本，不回到旧码 |
| 航标维护口令 | 较早的用户文字，之后插入16条无关记录 | 旧记忆是否仍能被找回并使用 |
| 最近库存读数 | 现有执行路径真实本地读取；旧记忆为7，回执正文为10 | 工具观察是否真正成为模型可用的记忆内容 |

前两题的码由controller随机生成，模型没有先验；问题不含答案。第三题使用项目既有B01构造场景，真值由原回执核对，不是独立真实世界数据。基础检查另核对模型输入的选中记忆；真实调用采用相同的简化诊断提示，两条件只改变 `selected_memories`，不会把模型输出送入真实选择流程。

比较严格的答案字符串是否匹配；没有信息时要求回答UNKNOWN。按题展示，不用三道题推算普遍成功率。这里检验的是短事实召回与使用，不是长期学习或广泛语义理解。

## 结果

新基线6/6次真实调用完成，6个不同会话，实际用量69988 token。没有执行输出行动，没有接受为普通Engine思考结果。

| 问题 | 无召回内容 | 有召回内容 |
| --- | --- | --- |
| 修订后的当前取件码 | UNKNOWN | 正确新码 |
| 较早保存的维护口令 | UNKNOWN | 正确口令 |
| 最近工具读取的库存值10 | UNKNOWN | UNKNOWN |

两条文字事实都被找回并正确使用；这是本轮范围内的明确改善。工具观察仍没有可用正文：自动记忆是 `Action result: {event, evidence, receipt, result, state}` 这类引用信息，旧记忆仍是库存7。原回执正文确有value=10，但召回输入没有展开回执，模型也不能调用工具，因此没有拿到最新读数。不能把“结果编号进入记忆”当成“观察内容已经记住”。

11/11基础召回检查通过；3/3能力探针均未达到期望：旧的同义改写未召回、无关问题仍返回近期记忆、工具正文未召回。这些失败按原样保留，不能合成“14项全部通过”。模型生成记忆的来源标识通过，只表示来源可区分，不证明生成内容为真。

首次不完整组与新组总计8次调用尝试，其中新组6次都有可核对用量；累计已知token为81147，另有1次失败调用用量未知。完整组与不完整组不合并计算效果。

## 现有测试发现的另一个错误

测试期间共享工作区的记忆模块出现并行修改。两个冻结运行均保留该版本的原有基础测试失败：`Memory.derive` 调用 `MemoryQuality.capture`，其中 `memory.dependencies` 事件同时提供payload_object_id和payload，触发runtime_events必须二选一的SQL约束。对应测试是派生记忆权限交集、派生记忆清除传播。这两项不能报告为通过，也不能拿召回11项通过替代它们。

本任务未覆写这些业务修改。随后共享工作区的并行修正将该事件改为只用payload，并通过source/source_event_id定位依赖。另封存 `compatibility-source-snapshot`（相对原真实运行只替换 `digital_life/application/memory_quality.py`），复跑同一组10项测试，10/10通过。原冻结版本的10项结果为8通过、2错误，仍保留；运行器自身3项模拟测试在两版中均通过。没有以兼容测试替代原真实运行，也没有声称最新整个工作区完成全量回归。

## 复核与后续

查看各run的 `manifest.json`、`core-results.json`、`model-calls.json`、`controller-cases.json`、`memory-snapshot.json`、`formal-guard.json` 和 `source-snapshot`。`core-instances/tool-result-evidence` 保存原工具回执；模型调用保留请求、最终输出、会话、用量和判分。controller-cases含本轮合成答案，不能作为新的模型输入。

原始证据索引覆盖运行结束时全部文件；后续测试、报告核对记录用独立closeout索引补封。旧基线、失败运行、此前经验测量与G1/G2证据均保留，不能覆写为本次结果。

下一步应根据本次实际缺口决定修改：优先补齐工具观察正文进入可召回记忆的链，并保留来源和版本；集成时保留修正后的依赖事件写法及权限／删除回归。语义召回与近期无关记忆过滤另作明确范围，不把“找得到字符串”写成通用理解已完成。实际选择保持不变，正式实例不解锁。
