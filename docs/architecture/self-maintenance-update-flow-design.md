# 自主维护更新流程 V0.1

2026-11-15。先设计再实现。人格成长关闭，CLI保留部署控制。

## 目标

让已授权项目源码修改自动形成带实际调用、回执、Git版本和部署基线的更新提案；由明确的CLI命令完成停止、构建、固定业务检查、部署独立思考与失败恢复。不是允许模型自行重启宿主。

## 核心规则

1. 仅捕获project_write/project_edit对digital_life包内受支持文本文件的成功、核验pass回执；普通资料文件不进入源码部署。
2. 原动作必须来自被接受的独立思考，并仍符合原项目授权。使用回执绑定的私有Git提交读取不可变内容，核对内容hash；不从可能随后已变化的工作区重新抓文件。需要project_version_save权限和明确版本。
3. 修改前hash必须等于活动部署中对应文件的hash；新建文件要求基线中不存在。已有草稿不等于活动版本，基线不一致时仅记录拒绝，不拼装未审阅的混合版本。单文件提案复用原64KiB上限。多文件关联修改仍应显式提交一个原有changes提案；首版不自动猜测组合。
4. 采集只产生proposal，不执行候选，不构建、不调用模型、不改实例生命周期。采集拒绝有日志，不撤销已完成的项目编辑。
5. CLI新增manage.py update --proposal ID --confirm 'UPDATE 实例名'。只更新既有实例，不创建实例；禁止唤醒锁仍需原流程显式解除。执行前显示提案与基线并检查无排队/执行中工作；正常停止并等待退出，绝不强杀清登记。
6. 构建候选、运行已有固定业务探针，检查失败则恢复原兼容版本；部署阶段继续使用检查点、独立思考验收和原watchdog。恢复已知旧版不重复模型验收，保留当前账本，不重放未知动作。
7. 更新期间出现新的用户停止命令、锁或其他运行器，取消自动启动。CLI持续监督新版本或已恢复的旧版本；Ctrl+C按原监督机制停止。

## 重要实现边界

现有固定探针是在临时目录运行候选代码，不是OS沙箱。临时HOME/Python隔离选项不能阻止候选源码访问本机其他路径。因此仅在操作者明确执行CLI update时执行该代码；不会因后台健康诊断或模型写文件自动运行。实现OS隔离后才能进一步讨论无人值守执行任意候选。

该流程接通的是“发现/接到问题 → 思考修改 → 提案 → CLI构建、检查、部署 → 验收或恢复”。发现问题仍用现有诊断/用户任务；不新增无限自动修复循环，也不声称任意问题能自动归因或修复。
