# 第二轮优化 PF01 分段诊断报告 V0.1

状态：PF01隔离分段诊断及旧实现解码／复制补测完成。01保留原始分段证据，02补齐计数；二者独立报告。未修改产品代码、未操作正式实例或调用真实模型。

## 看到了什么

完整“8模块／17段历史”合成样例，在增加观察工具后耗时154.410秒。互斥计时表明，来源与使用资格检查占146.193秒（94.68%）；收集资料、构造输入和保存结果本身的成本很小。因此下一步应改变同阶段资料读取和来源处理的组织方式，而不是削减输入特征。

上一轮137.928秒是无观测的独立样例，154.410秒是本轮带SQL摘要和行计数的诊断，两者不作为优化前后的速度对照；观察工具自身有开销。这里的互斥时间可相加，原方法的包含时间不可相加。

| 实际工作 | 互斥秒数 | 说明 |
| --- | ---: | --- |
| 来源／使用资格检查，所有阶段合计 | 146.193 | 包含收集、注册、输入组装、调用前、结果保留等处的检查 |
| 收集和计算资料，排除上述检查 | 2.834 | `_primary/_recall/_conversation/_features/_contexts` |
| 输入构造，排除资料收集与上述检查 | 1.295 | `StrictEngine.prepare`的剩余时间 |
| 输入依赖登记，排除上述检查 | 2.087 | `ToolLearningRuntime.assemble`的剩余时间 |
| 生命周期／记账等剩余时间 | 1.826 | 主调用中尚未归入上述操作的工作 |
| 结果整理保存，排除上述检查 | 0.129 | `_finish`；其它保存成本仍分属登记或生命周期 |
| 模型适配，排除调用前检查 | 0.035 | 确定性替身；不代表真实LLM延迟 |
| 测试入口／出口等剩余 | 0.012 | 观察器覆盖窗口与主Engine窗口的差额 |

完整Engine打印154.398秒，与观察器154.410秒差约0.012秒。没有单独测真实模型；替身的外部传输在受管子进程执行，子进程内存中的计数不会冒充父进程计数。

主要重复查询形状包括：按实例／ID读取`object_registry.kind`、按来源读取活动变更屏障、读取`policy_epochs`、读取当前配置版本，以及`PRAGMA user_version`。例如`input_use`内仅对象种类查询和屏障查询就各执行48,264次。

## 为后续设计提供的接口定位

- `ToolLearningEligibility._upstream(token, scope, scan_budget)`先读取依赖图、解码metadata并保留路径；`_check(...)`随后按每个返回路径读取Ref、验证版本、权限、epoch和屏障。不能把返回路径按来源ID直接去重，否则read/delete和不同Scope等会丢失。
- `StrictEngine._qualified_fields(..., stage)`及`ToolLearningRuntime._qualify(..., stage)`提供检查阶段边界；共享资料应局限于该阶段，下一边界重新开始。
- 可优先设计固定实例内、已授权范围中的registry／revision／dependency行集中读取，以及不可变metadata材料复用；用途和接收者判断仍分别执行。
- 真实SQL／文件读取继续计量；逻辑图节点／边数量和原上限仍逐消费者保持。不以一条批量SQL逃掉逻辑扫描限制。
- 主库之外还有控制库、其它连接／进程和工件文件；本连接`total_changes`不能证明全部一致。遇到跨连接变化，尤其旧事务仍持有旧快照时，应使阶段失效并拒绝，不能只清缓存后继续使用旧快照。
