## 1 本次任务与结论

用户要求先出具报告与交接文档，记录本次任务和修改，便于其他 agent 接续。本报告承接讨论中的标准：没有人的新指令时，系统能够从经历中产生值得探索的问题，主动获取信息，并根据反馈继续或调整探索。

结论：现有分层、持久化、业务模块和执行底座支持增量实现，无需重建主系统；但当前主路径仍以外部任务为中心，必须扩展活动生命周期、内部问题来源和观察后的再思考机制。不是仅改提示词或增加定时调用即可完成。

本结论不代表现有版本已达到自主探索标准，不证明意识或主观生命体验。这里只评估工程可承载性，不引用外部理论作为实证。

## 3 操作性标准

“无输入”在此指无人新下指令；系统仍可接收时间、工具结果和环境变化。自主性要求以下因果链可追踪：

经历／观察 → 发现知识缺口 → 发散候选问题 → 选择问题 → 观察或实验 → 对照预期 → 修正认识 → 继续、休眠或结束。

每次模型调用可以独立，连续性由显式状态和记忆承接。更高调用频率、随机生成问题、定时独白和写出“我很好奇”，都不足以单独通过验收。

## 4 建议的职责划分

| 职责 | 建议落点 | 产物 |
| --- | --- | --- |
| 发现异常、冲突、未知与联想，产生候选问题 | cognition 及探索应用服务 | 带证据来源的候选问题 |
| 按兴趣、价值、可行性和成本取舍 | goals、values、states、decisions | 选择依据、未选理由、预算 |
| 安排再次关注的时间与条件 | scheduling 及探索协调用例 | 到期任务、事件订阅、休眠条件 |
| 多轮推理、观察及恢复 | engine | 轮次、独立请求、执行结果、后续状态 |
| 保存经历与修正认识 | memory、cognition、learning | 可追溯证据及认识版本 |
| 获取信息 | 既有工具与授权执行链 | 来源明确的观察，不把工具结果直接当作可信指令 |

建议增加 `application/exploration.py` 作为跨模块协调用例；名称尚未冻结。不要在 runtime 入口中直接堆叠认知规则，也不要引入第二套主框架。

## 5 必要的增量契约

### 5.1 问题及兴趣

建议显式保存：问题 ID、内容、来源类型、触发证据、父问题、关联记忆／目标、候选解释、可验证条件、状态、最近关注时间、下次唤醒条件、已尝试方法、探索成本和结束理由。问题可跨多个活动存续；问题与活动不应一一绑定。

候选状态：candidate → selected → investigating → resolved／abandoned；调查中可进入 dormant，满足条件后再进入候选或调查。每次转换保留理由与版本；这些是拟议状态，不是现有数据库枚举。

兴趣是多个探索经历形成的较长期偏置，需要保存支持经历与变化原因。不得用一次模型自述直接确认为稳定兴趣，也不应自动改写人格和长期价值。

### 5.2 多轮活动

区分 activity、认知轮次、thought_request 和 thought_attempt：新观察后的下一轮是新请求；同一请求的传输重试才是新 attempt。每轮明确输入证据、配置版本、预算、取消及权限 epoch，保留一次接受与过期结果隔离。

模型输出建议按用途分契约：问题发现、探索选择、行动提案、观察评估。不要强迫每次思考都输出外部动作，也不要把自由文本 explanation 当作状态转换依据。

### 5.3 结果与完成

工具成功只证明动作执行结果；还需判断观察是否充分、假设是否受到支持、问题是否满足解决条件。证据不足可以继续、暂停或放弃。普通单步任务仍需保留明确完成规则，避免一律进入无限探索。

### 5.4 内部触发与感知

引入有来源的内部触发，如未解问题到期、预测待核验、证据冲突和探索复盘。来源应区分用户、承诺、工具观察和内部生成。内部想法是解释或候选，不作为外部观察证据。

先用既有工作区读取能力验证主动感知闭环；未来新增外部来源另行接入工具注册、权限、原始信号记录和来源验证。

## 6 驱动与节律建议

初始驱动仍需设计者赋予倾向，具体问题由经历生成。建议综合预期信息收益、可取得的学习进展、历史兴趣、价值相关性和可验证性，扣除成本、重复度与不可约噪声。系数和阈值需隔离实验校准，不在本报告虚构有效数值。

发散阶段生成有限数量、具有不同解释或观察路径的候选；收敛阶段选择少量可验证问题。新颖不等于有价值；自报信心不等于实际学习进展。观察后应以预测检验、解释区分或独立测量评估收益。

采用事件唤醒与有上限的周期复盘，设置探索总预算、每问题预算、重复抑制、退避和休眠。休眠是正常结果，不以持续消耗模型调用证明生命连续性。

## 7 实施顺序与数据库边界

1. 复核并冻结问题、轮次、观察评估、触发来源和结束判定契约，逐项映射现有 SQL，确定复用与新增字段。
2. 扩展引擎多轮请求身份、观察回流和恢复路径；保持现有任务回归成立。
3. 接入问题记录、发现与选择；实现来源追踪、去重、休眠和预算。
4. 在隔离环境用有限工作区完成端到端探索验证，再决定是否扩展感知通道。
5. 增加只读可观察信息，展示当前关注、证据、下一次关注条件及停止原因；之后再考虑管理面板调整。

数据库应先审计生成器、约束和资源发布方式，通过正式迁移维护，不手改正式实例或两份 SQL。迁移应验证旧任务兼容、历史请求不变、崩溃恢复、回退策略和新增状态转换。本文未给出已可执行迁移方案。

## 8 拟议验收方案

| 场景 | 应观察到的行为 |
| --- | --- |
| 初始材料后不再发指令 | 系统从材料产生有来源的问题，自行选择允许的观察 |
| 反例材料 | 后续解释、信心或计划发生可追溯变化，不只是追加原结论 |
| 读取成功但证据不足 | 动作完成而问题保持未解决，继续或明确暂停 |
| 重启与中途崩溃 | 保留未解问题与观察证据，不重复已接受结果或副作用 |
| 重复材料与随机噪声 | 抑制重复并适时退避，不靠无穷问题耗尽资源 |
| 预算耗尽与停止 | 有明确休眠／停止原因，遵循取消、权限和实例锁 |
| 对照实验 | 关闭问题生成、记忆或反馈后，与完整机制比较问题延续和修正能力 |

记录自主问题来源、验证证据、认识变化、重复率、成本和跨重启连续性。阈值、样本数与盲评规则需另行预注册；本报告不宣布验收通过。既有工程测试不能替代这些行为实验。
