# T12 健康维护与自更新详细设计

V0.1；设计基线／待隔离实证。先设计、后实现、再冻结验收；不部署、不重启当前实例。

## 目标与生命工程含义

健康是维持身份、组织、核心功能和连续关系，并在扰动后恢复可接受运行状态的能力；不把进程存活或所有指标加总当作健康。沿用项目研究 `docs/research/digital-life-health-and-self-maintenance.md` 的稳态、稳健性和韧性定义，认知正确性与主观体验仍不冒称已验证。

形成可检查的闭环：观测→诊断→有限修复计划→授权→执行→独立复查→恢复／降级／求助。源码更新走另一条闭环：提案→冻结基线→生成候选→独立临时实例验证→CLI部署→启动及运行观察→失败保留或回退上版。两条闭环均受停止锁、权限和预算约束。

## 复用与缺口

复用 HealthMonitor 分维度扫描、MemoryQuality 可重建索引、Recovery 未知副作用对账、Releases 不可变版本、Deployment 准备／激活双握手及 watchdog。既有回退不重置数据库：保留当前身份、记忆、历史、schema与真实副作用，不把回退程序等同于时间倒流。

补齐自动维护的有限预算、修复前后证据、源码提案来源、候选独立核验、稳定证据绑定。加强发布完整性：拒绝额外文件、篡改缓存及不完整候选；候选兼容声明须涵盖实际数据库版本。未知／坏数据不伪造健康，也不擅自删除记忆、重建身份、修改权限或恢复旧数据库。

## 模块、数据与接口

新增 `SelfMaintenance` 负责健康计划与运行时维护；新增 `SourceUpdates` 负责源码提案和候选验证。配置、计划、结果与提案存于已有不可变 runtime_events 工件（maintenance.* / source_update.*）；版本、切换、回退继续使用 control.sqlite 原表。没有重复身份／记忆／发布表，也不自动迁移生产schema。

- maintenance configure(enabled, auto_repair, max_repairs, actor)：默认关闭，auto_repair默认false，max_repairs为1—3；仅停止且无运行进程可配置。新配置是新预算代次，不自动重置预算。
- diagnose：存储完整性、身份、工作区、资源、派生索引和未知外部效果；语义认知、模型推理质量标unknown。索引未启用是not_applicable，不是故障；普通索引水位落后仅需同步，不报严重故障。
- plan(kind, key, actor)：白名单仅 `restore_workspace` 和 `rebuild_index`；前者只创建缺失的空目录，不宣称恢复文件；后者只重建可再生派生数据。计划绑定配置、故障事实、索引源水位及实例。拒绝symlink、非目录工作区、核心存储/身份异常和未决效果下的自动修复。
- repair(plan, actor)：控制者可在停止、无进程时显式操作；自动路径只在已授权 Runtime 内、配置允许、预算未耗尽时执行。协调锁先于事务，执行前重查事实；源变化或计划过期不执行。每项计划至多一次，失败也消耗预算，不循环重试。执行后独立复查目标，不把函数返回当作修复成功；其他维度unknown仍保留。
- runtime tick：配置启用时每30秒最多一次诊断，每次最多一项自动修复；自动预算按配置代次累计最多3次。只作用于已有授权进程，不部署、不唤醒、不清停止锁。超出白名单的故障保留降级与求助记录。
- status/context：配置、剩余预算、诊断、修复与源码状态；思考只放最近诊断摘要及明确能力边界，不全量附历史或凭据。派发和接受时配置快照变化拒绝旧请求。

## 源码提案与权限

控制者可CLI提交 `changes`（1—5个相对路径→UTF-8全文，单文件≤64KB，总计≤128KB）及 base_deployment、reason、key。只允许既有包内 digital_life/ 下的代码/资源格式；拒绝绝对/父级/隐藏路径、删除、符号链接和控制数据库路径。支持新文件但不支持依赖安装、自动数据库迁移或任意shell补丁。

系统也能通过现有 `write_note` 行为提交 `maintenance/update-*.json`：普通审批模式仍需行为审批，open模式沿用现有授权。该通道仍受 write_note 的16000字符上限限制，CLI提案使用上述128KB上限。仅当maintenance启用时消费成功工具回执中的原始参数；验证归属、实际回执哈希及提案基线，记录模型请求/动作/结果来源。提案失败只记录拒绝，不把已经成功写笔记的行为改成未知。该行为只生成提案，不修改运行源码。无需增加工具schema或跳过既有行为权限。

CLI build 使用当前 active release 为基线，复制到独立候选目录，再应用变更并stage。基线不匹配、待更新或篡改时拒绝，构建幂等。运行版本和宿主验证器不随提案直接改写。部署、启动和唤醒始终经既有CLI；open行为权限也不隐含允许正在运行的进程热替换自己。

## 独立候选验证与回退

CLI validate 在新临时目录运行固定宿主探针：候选模块导入、完整schema初始化、有限文件目标、实际受限工具、独立内容核验及连续两次独立思考。使用固定模型适配器，无远端调用、无正式实例输入，父进程独立核验文件与临时SQLite结果。候选实际数据库兼容范围必须包含目标实例的当前版本；验证前后检查发布内容与目标版本基线，提案不能自行宣布通过。

证据记录候选hash、base_deployment、目标schema、固定探针版本和结果。验证通过不会自动部署；验证失败不修改active。后续CLI deploy仍必须经过原双握手及运行监测，涵盖运行失败、唤醒/激活失败和heartbeat失效；用户停止不得触发回退重启。旧版本兼容性也须重查，不兼容则保持停止/降级，不伪造成功回退。

“隔离”指临时数据目录、子进程、无模型推理与清理后的环境，不等于操作系统安全沙箱。执行候选代码需要信任其代码；探针是有限工程验证，不能证明任意自修改安全或全面正确。当前正式实例从不作为候选探针的数据源。

## 验收矩阵与完成范围

临时实例验证默认兼容、配置和停止门控、未知分维度、目录缺失/冲突/symlink、索引缺失/损坏/源变化、计划CAS/TTL/幂等、预算与失败不重试、真实自动维护闭环、配置输入快照及面板历史、控制者和真实工具回执提案、非法变更、基线冲突、候选缓存篡改/额外文件、实际探针成功/语法或运行失败/超时、schema不兼容、验证不激活、部署前后失败及watchdog回退、用户停止优先、身份记忆历史保留。全量回归与正式实例只读基线比较后才能将T12标完成。真实LLM生成补丁与长期自愈稳定性留给明确的后续实验和T13，不冒充已验证。
