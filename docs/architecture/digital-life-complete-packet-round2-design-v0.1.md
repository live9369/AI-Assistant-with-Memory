## PF02：共同取资料、分别判断、立即失效

| 资料或结论 | 规则 |
| --- | --- |
| 同实例、相同查询完整参数的登记、修订、依赖关系行 | 阶段内按需共享固定事实，不生成许可 |
| 已验证依赖元数据与原始工件 | 保留摘要、行映射及原文件身份；文件变化拒绝继续使用 |
| 相同完整token、Scope和上限的来源图 | 可共享图准备结果；保留有序重复路径、read/delete关系及每消费者逻辑预算 |
| 人格、记忆、关系、目标分别使用某句原话 | 分别保留字段绑定、用途、接收者和当前资格，不按文本合并 |
| 当前版本、ACL、epoch、屏障、停止、健康、用途和接收者判断 | 原逐项检查保留，不把事实缓存当作允许使用的结论 |
| 回调、模型或工具调用、下一阶段 | 结束或重新创建共享读集，不能把本阶段资料当作下一阶段的新鲜许可 |
| 主库其它连接／进程提交 | 独立观察连接发现变化后拒绝旧阶段；不能在旧快照里清空后继续 |
| 本连接写入 | 清空共享事实；原权威判断和事务检查继续，写入后的首次资料重新读取 |
| 控制库变化、数据库替换、工件变化或无法确认一致 | 结束共享阶段并报错，下一入口重新检查；不自动重放外部动作 |

身份仍由原token、scope和每条完整依赖表达；这些字段包括实例、原件、修订、视图、定位、时间、单位、条件。用途、接收者、原关系路径不被合并。历史材料保持历史含义，当前状态由原live检查负责。

## PF03：接口与生命周期

新增内部 `PhaseReadSet`，只由明确的本地只读owner verification boundary安装。ContextVar引用限定store、连接和实例，退出与异常关闭并清空，复制context不能复活。未知权威实现不自动获得共享。

读取接口是固定事实查询目录，不是任意SELECT缓存。首批只用于来源上溯的登记／修订／依赖事实；不缓存控制许可或修改SQL。每个键包含查询名、同实例约束与全部参数，按需首次读取，后续消费者共用；按原迭代器逐行取出并通过原meter逐行收费（不预读64行，以免在逻辑上限前额外读料），单个请求保持原LIMIT。查询／图缓存至多4096键，事实、图及文件跟踪合计至多4MiB编码内容；文件跟踪另设4096项硬上限，超过后原路径读取，不增加任何业务cap。不预读全库，不用另一个用途的权限预取资料。小批合并先采用同键需求合并；跨键IN预取没有证据支持，本轮不做。

新读集保留主库独立只读观察连接的data_version，数据库dev/ino及主库／WAL状态、控制库及WAL状态、用到工件的身份和时间状态。检查入口／出口核验，首次读到的文件仍经过原O_NOFOLLOW与size/hash验证；变化不能只清缓存后继续旧事务。文件状态是变化探针，不宣称能对抗具有任意系统权限的恶意写者。当前控制检查仍实际执行。

PF04先接入按需事实读取，不改遍历结果；PF05再共享图准备。图键包含完整token、scope、max_nodes、max_rows、实例；保存成功结果与实际逻辑行数，命中仍扣调用者scan_budget，低预算回到原逐行路径以保留失败位置与类别。不同入口／purpose／recipient的资格判断从不共用，任何图输出均提供独立副本。失败、部分结果不保存为完整图。

每次_check依然执行principal、source、version、epoch、barrier、执行状态检查。所有通用authority和actual callback的原核验边界保留；未知或可写callback禁用新共享。现有本地owner旧memo也必须受新阶段新鲜度检查约束。

## PF04实施校正

- 原本连接写入及COMMIT需要区别：UoW开始前检查外部变化，结束后创建新generation，清空可变查询事实与所有旧引用证明；本地许可memo键也包含generation。提交后文件清理窗口再次检查，事务体原异常不被清理异常覆盖。
- 合法本连接提交不意味着已验证原件被修改。不可变bytes／依赖元数据可在原meter操作内保留，但文件跟踪跨本连接提交持续检查；新verification阶段首次读取仍重新核验hash。不同阶段的当前资格从不复用。
- 文件跟踪512项的早期实现不足以容纳完整合成样例，造成反复清理与实际读量增加。改为独立4096项技术上限，并纳入同一4MiB编码预算；这不改变业务扫描、项数、字节、tokens或时间cap。内部跟踪溢出禁用新共享，相关原件不走bytes／metadata命中，走原完整校验路径，可能按原预算拒绝。
- 新增事务、跨连接变化、提交清理窗口、原异常保留、目录替换等针对性用例。早期完整流程失败记录保留，不作为完成或提速证据。

- PF04进一步修正：512个查询键不足以容纳完整来源图的登记、epoch、依赖和原件定位，新增定位读取反而使固定子预留先耗尽。技术查询键上限改为4096，仍受相同4MiB编码预算约束；原业务资源cap保持完全不变。

- 为区别本连接提交与外部提交，额外保留主连接data_version（不随本连接提交增加）和独立观察连接data_version（可观察旧快照期间的外部提交）。UoW入口核验；结束清可变事实与许可generation；纯引用映射仍受原total_changes及双连接外部变化探针保护，不把外部提交重设为合法基线。提交后清理窗口再检。
- 4MiB不足时先淘汰可重新读取的SQL事实，为文件完整性跟踪让位；文件跟踪本身超限才禁新共享。目录身份也被检查。所有工件read_artifact路径都登记文件状态，依赖metadata命中同样检查。
- PF04中间完整验证 fixed04通过：142.494秒、1116899条实际返回行，未知预留0。它不是最终源码或提速证据；前三次失败及初始own-COMMIT误判记录保留。

## PF05整合补充

图缓存保存完整token／Scope／节点与行上限、完整有序路径及原逻辑行数。命中仍扣逻辑扫描预算，不足预算回原逐行流程；图只共享准备资料，不提供资格结论。完整依赖行集仅在实际返回行数小于所请求LIMIT时标为完整；跨其它LIMIT复用时仍按原前缀和逐消费者预算处理。

metadata缓存现在只保存JSON结构与完整依赖行绑定的纯核对，Ref与修订投影每次重新核对；同连接变更不能使旧动态映射继续有效。所有Store工件缓存入口统一跟踪文件，避免只保护TL入口。查询事实每次读取先检测本连接写入计数。

_check入口／出口保留完整新鲜度检查；_upstream在这个只读内部过程不再重复同样的全文件检查，直接调用_upstream时仍自行检查入口／出口。LocalEligibility直接调用入口仍查新鲜度，只有已位于_check内的纯只读owner核对复用外层探针。

## 诊断驱动的PF05整改

PF05第一次整合诊断表明：整根来源图1625次查找、0次命中，累计准备约482MB编码。字段本来已按相同根去重，而写事务又正确地结束上一代资料；因此不能为了命中而跨代保留许可。整改重点转向不同根共有的节点准备材料及其Scope键；根图采用按重复需求准入，避免独特根承担整图编码成本。具体节点身份／原件摘要与动态映射失效规则在PF05实施记录先定稿后实现。

4MiB只指阶段读集保留的事实、图、节点准备证明及文件记录的编码大小，包含键和值；不包括Python容器开销、当前输出工作缓冲，也不是整个进程或原PhysicalReadMeter原件缓存的总内存上限。原meter实际读取仍受原预留与512MiB等业务预算约束，未提高这些cap。溢出不允许省略检查。

PF06上一版39新增故障加必要旧机制共118项通过，源码前后稳定；PF05整改后重新运行，不将旧版通过自动套到新实现。
