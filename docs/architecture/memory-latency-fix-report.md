# 记忆准备耗时修复报告

日期：2026-11-14。已实现，相关测试通过。

**2026-11-15 计时更正：原 16.117 秒是未执行运行器启动检查的快照测试路径，不代表启动后的正常对话准备。按正式启动逻辑完成实际完整性检查后，同类完整 prepare 实测 0.579 秒。详见文末。**

## 修复

- 派生记忆的来源权限交集已经为空时，立即结束该分支，缓存本次调用中的拒绝结果。此前仍反复遍历多个分支。
- 将昂贵的当前版本、来源及权限检查放到相关性排序之后；按排名检查，取满原有数量即结束。没有改变评分公式、特征信息或可读性规则。
- 增加 `memory.retrieval_timing` 日志：加载数量、评分数量、实际校验数量、选中数量和耗时；不写私有正文。
- 不使用跨请求权限缓存，来源撤回及账户隔离仍实时生效。既有索引路径保留；关闭索引模块时的廉价文本扫描回退仍存在，本轮未改变模块开关。

## 测量

使用正式数据的 SQLite backup 快照和完整 blobs 副本，未启动副本运行器，未调用模型，未修改正式身份、记忆或历史。测量结束后副本保留禁止唤醒锁。

| 项目 | 修复前 | 修复后 |
|---|---:|---:|
| 同一条慢记忆的来源权限检查（同一快照、无 profiler） | 3.565 秒 | 0.088 秒 |
| 完整输入准备 | 此前正式三轮调用前合计 130—167 秒，含等待 | 本次快照实际 prepare 16.117 秒 |
| 本次记忆检索 | — | 0.244 秒 |

完整准备前后不是严格同条件对照：此前数据包含调度等待，测试后又归档了合成资料。因此不能把两者差值全部归因于修复。单条慢记忆的对照在同一快照上完成，可以直接比较。

检索加载 204 条，评分 151 条，仅对排名靠前的 9 条做检查后取得 8 条可读结果。与原检索流程在同一快照、同一输入上的最终 revision 顺序完全一致。剩余约 16 秒属于完整准备的其他工作，尚未在本轮逐函数拆分；本报告不宣称聊天端到端仅需 16 秒。

## 验证与边界

`tests.test_experience_return`、`tests.test_cognition_provenance`、`tests.test_account_management` 共 26 项通过（13.919 秒）。覆盖旧来源撤回、共享依赖分支、拒绝高排名后继续取结果、当前与历史版本、跨账户私有信息隔离。

测试中首次两条新增用例的夹具遗漏 evidence 来源，已补齐；首次账户 HTTP 用例受本机端口权限限制，获得工具授权后全部通过。

本轮不处理语义重复候选、回复“未保存”表达不一致，以及管理进程数据库锁异常的独立根因；缩短检索事务不等于证明锁异常已消失。

证据：`outputs/memory-latency-fix/measurement.json`。复现脚本：`scripts/verify_memory_latency_fix.py`（只接受首次创建的快照目录，避免覆盖）。

## 2026-11-15：准备耗时口径更正

为解释 16 秒，额外在已有快照上做一次按行计时（不调用模型）：总计 15.918 秒，其中 GoalRegulation.context 占 15.174 秒，检索 0.413 秒。快照脚本只初始化 Store，没有执行 entrypoints/runtime.py 的启动完整性检查和 _startup_integrity 登记，所以 StateCollector 和 CurrentHealthEvidence 回退到全库检查。正式运行器启动时原本已经执行并登记该检查。

按运行器实际逻辑先执行完整性与外键检查（确实通过后才登记文件身份、schema、configuration），再计 prepare：启动全检 9.132 秒；完整准备 **0.579 秒**，其中记忆检索 **0.239 秒**，健康探测 **0.401 毫秒**。仅一次针对性核对，不代表生产端到端聊天时延。未触及正式实例或调用模型。

原脚本已修正为先做实际启动检查，再单独计输入准备；原始 16 秒证据保留，不能作为常规热启动准备指标。证据：`prepare-stages.json`、`prepare-warm.json`，位于 `outputs/memory-latency-fix/`。

“单条慢记忆”仅为瓶颈对照样本；实际此次检索加载 206 条记录，评分 153 条，依序校验 9 条后取得 8 条。来源权限检查目前仍按候选及其依赖逐条执行 SQL，不是每轮仅检索一条，也不是批量查询已完成。索引关闭时仍加载有效记录，后续改为索引候选不能冒称本轮已实现。
