# 自主维护更新流程交付报告

日期：2026-11-15。状态：核心实现、必要隔离验证与正式部署验收完成。

## 这次补齐了什么

已授权的项目源码编辑，在真实工具回执核验成功后，可以自动生成更新提案。提案绑定实际独立思考、工具意图、结果、私有Git提交、文件前后hash和原部署编号；下一轮思考能从任务观察中看到提案编号与“尚未部署”状态。

普通资料文件不进入源码部署。缺少版本、版本或回执不符、工作草稿与运行版本基线不一致时记录拒绝原因，保留已完成编辑，不顺带部署其他草稿。首版只自动生成单文件提案；相互依赖的多文件更新继续用原changes提案显式组合，不自动猜测。

新增CLI：

```sh
# 列出已有提案及检查记录，不启动模型
python3 -m digital_life --data work/primordial00-first-wake maintenance status

# 明确执行一个已有源码提案，并保持终端监督
python3 manage.py update --proposal PROPOSAL_ID \
  --confirm 'UPDATE primordial00-first-wake'
```

更新命令核对提案基线、保护锁和未完成队列工作，正常停止并等原运行器退出，再构建、执行固定业务探针、部署。检查失败时恢复原兼容版本；部署失败沿用原检查点回退与watchdog。恢复已知旧版不重复真实模型验收，仍保留当前账本，不重放未知动作。新的用户停止、锁或其他运行器优先，不能被本次维护的自动恢复覆盖。

源码编辑、提案生成不授予部署权限，也不直接执行候选代码。部署继续由CLI控制。

测试中发现原首次维护用0作为上次执行时间。在当前计时起点接近0的环境中，会等约60秒才首次检查，导致原8秒自我修复用例失败。已改为初始化时直接使首次维护到期，后续仍保留原60秒调度间隔。没有提高活动预算、延长验收等待或放宽健康条件。修复后的实际进程3项全部通过。

一次复核在修改测试源码时触发了发布基线不一致拒绝；后续冻结源码再验证，没有绕过版本检查。

## 日志与可追溯性

- `source_update.proposed`：不可变提案及来源。
- `source_update.captured`：工具到提案的接纳或拒绝原因。
- `task_loop.observed.source_update`：下一轮实际可见的提案状态，不伪装成原工具执行权限。
- `source_update.built / validated / pipeline_result`：构建、探针和更新结果。
- 原部署独立思考、检查点和回退日志继续保留。

## 边界与未完成项

这是“授权任务修改 → 自动提案 → CLI检查与部署 → 验收或恢复”的受控闭环。现有健康诊断与白名单修复继续运行，没有新增无边界的模型自主修复循环；不能声称任意异常都能自行定位和修好。

现有探针在临时目录执行候选代码，临时HOME和Python隔离选项不等于OS沙箱。该执行仅由操作者明确运行CLI触发；本版没有实现无人值守执行任意候选源码的完整隔离。进一步开放前，应补独立于可编辑源码的控制器与进程权限隔离。

受保护schema4的原兼容和来源限制保留；首版不让任意修改继承已审阅的schema4桥接能力。原数据库、身份、人格和权限保持原规则。
