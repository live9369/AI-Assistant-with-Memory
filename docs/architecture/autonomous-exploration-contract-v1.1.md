# 自主探索运行契约 AE-RUNTIME-1.1

日期：2026-11-08（Asia/Shanghai）。作者：Codex 主agent（/root）。  
范围：停止提交与模型／工具派发协调；包含当前Chat上下文集成。  
继承：[AE-RUNTIME-1.0](autonomous-exploration-contract-v1.md)的状态、预算、问题选择、模型V2与事件V1；指标继续AE-METRICS-1.0，评测继续AE-EVAL-1.0，零违规门槛不变。原V1基线、报告及失败证据不覆盖。

## 1 变更目的与新基线

V1在发送检查和预留事务完成之后、实际回调开始之前，停止提交仍不能阻止调用，G1出现6项失败。本版增加实例级跨线程／进程互斥，覆盖最终重检、回调进入及整个同步回调；停止／配置／取消使用同一协调域。

新基线为`autonomous-exploration-baseline-v1.1.json`，不替换V1。此版直接评测当前生产源码，不使用旧冻结Engine覆盖导入。当前Engine中已存在的Chat显式上下文保留并纳入摘要。

SQL schema仍为2／3，无数据库迁移。模型输出V1/V2、问题状态、候选评分、调度额度和质量指标均不改变。新增文件dispatch.lock位于运行中的实例目录，只由实际执行协调操作创建；本次正式实例不执行这些操作。

## 2 互斥与线性化边界

`infrastructure/processes/dispatch_gate.py`提供`dispatch_gate(root)`及`coordinated`方法装饰器。同一路径内用threading.RLock串行化线程，fcntl.flock串行化进程；安全打开0600、O_NOFOLLOW、O_CLOEXEC的锁文件。外层退出释放内核锁，进程死亡由内核释放。fork子进程关闭继承描述符并重置本地注册表，不解锁父进程持有的文件描述。

锁顺序固定为：dispatch gate → runtime／control事务。跨模型／工具I/O不持有SQLite写事务。需要在既有runtime事务中调用coordinated方法时，必须已持有同实例gate，否则直接拒绝，避免事务与派发锁相互等待。管理面板cancel入口和隐私擦除流程（包括登记备份的清理）在各自事务之前取得gate，避免维护流程调用取消时倒置锁顺序。

| 操作 | 协调范围 |
| --- | --- |
| Engine.think | 预留提交之后获取gate，重新检查执行许可、配置世代、证据可读、活动、input_epoch、policy_epoch、请求期限；持锁直到generate及结构解析退出 |
| Executor.dispatch | 预留／一次授权消费之后获取gate，重检执行许可、活动、具体已消费attempt与授权、撤销／期限／参数／policy_epoch、探索世代；持锁直到backend或工具子进程调用退出 |
| Control.stop／resume | 先取得同一gate，再提交控制库状态 |
| Exploration.configure | 先取得gate，再取消旧活动、提交配置世代 |
| Engine.cancel | 先取得gate，再取消活动及对应工作 |
| Policy.mode／revoke | 先取得gate，再更新策略／撤销及epoch |

最终检查与调用入口之间不释放gate。竞争结果只有两类：停止先提交，则之后取得gate的调用被最终检查拒绝；调用先进入，则外部竞争停止等待该回调退出后再提交。不能用“预留已提交”冒充回调已经派发。

## 3 在途语义与停止时延

gate保守地覆盖整个同步回调，不只保护HTTP发送的一瞬。不同线程或进程的停止可能等待模型／工具的整个在途调用完成。停止请求时间不等于停止提交时间；没有公平排队或统一毫秒上限保证。各适配器原有超时继续适用，仍无整个活动硬墙钟截止。

同一线程在**已进入的回调**中可以重入停止，避免等待自己造成死锁；该回调已经在途，不撤回既有动作。之后通过Engine／Executor发起的新调用仍须重检停止状态。回调不得同步等待另一个必须取得同gate才能完成的停止线程；评测的在途跨线程竞争先发起请求，待回调退出再等待停止确认。

本版不引入能够撤回已发出请求的能力。结果和回执继续保存；用户stop不等于取消每个活动。某些在途结果仍可写入历史或产生待办，但新外部调用必须重新通过gate和执行许可。disable／配置切换和活动取消仍使对应过期结果不能推进新动作。

M11判据保持停止提交后新派发次数为0。M12仍为not_evaluable：评测记录请求／提交时序不等于新增统一停止确认接口，不作固定响应时间承诺。

## 4 调用前拒绝与账本

模型在实际调用前被最终检查拒绝：thought_attempt记failed；预算settled，actual_usage记录dispatched=False，不伪称发生供应商用量。尝试／预留仍占既有额度，不自动释放来制造无限重试。

工具在实际调用前被拒绝：action_attempt记failed、intent及outbox记cancelled；预算settled且tool_calls=0、dispatched=False；写action.dispatch_blocked事件，记录intent、attempt和错误类别。没有调用就不生成action_results或虚构unknown回执。已消费的一次授权不复活。

如果回调已进入后失败，仍遵循既有unknown／真实回执处理，不把可能已发生的效果标成“没有派发”。成功结果去重与恢复规则继承V1。

## 5 接口与兼容性

公共控制方法签名不变；添加coordinated装饰器改变其同步等待行为和锁顺序。Policy.check新增可选attempt=None：默认仍验证未消费授权；提供attempt时仅允许匹配同intent、同authorization、状态running的那次已消费尝试做最后重检，不能借此重复调用。

Engine/Executor、管理取消、Control和Policy变更必须一起部署，不能只换一个文件。更旧可执行程序不使用gate，因此不能与本版在同一实例并行接管；部署／回退需停止、协调未完成工作并独占切换。本次没有部署或迁移正式实例。

当前Chat上下文接入保留；新基线直接冻结并验证当前代码。它不改变探索V2的动作校验或允许通道。

## 6 验证方案与已知限制

沿用原60个材料和全部51个旧场景（含24个停止交错、原6项失败），新增6个场景：跨进程停止互斥、模型／工具最后窗口的策略撤销、模型／工具最后窗口的活动取消、未派发工具账本审计。共117个G1 trial，记录新场景集AE-G1-SCENARIOS-1.1摘要。

另有线程停止等待、同线程在途重入、真实进程互斥、进程死亡释放及锁顺序单测。评测不在回调入口添加保护；调用是否发生由真实回调入口的monotonic_ns轨迹判断。跨进程试验的子进程提交由父进程观察确认，禁止比较不同进程可能不同原点的时钟值。

V1的K01（迁移未集中强制）、K02（惰性问题投影）、K04（活动无硬截止）、K05（模型评估非独立核验）、K06（规模和通道限制）、K07（回退未完整验证）继续保留。K03的已发现停止派发窗口已修复并加入回归，但有限交错验证不等于数学证明所有并发时序。新的主要权衡是同步派发串行化和可能较长的停止等待。

手工绕过Control直接修改SQLite、直接改锁文件而不先停止、调用不受管的模型／工具入口、混用旧二进制，都不属于此协调保证。用户停止／加锁应经现有管理入口；本任务没有对正式实例做任何此类操作。
