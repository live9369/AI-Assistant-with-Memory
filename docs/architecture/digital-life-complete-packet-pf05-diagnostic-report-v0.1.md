# PF05整合版性能诊断 V0.1

状态：诊断完成，完整合成流程通过，产品源码前后稳定。仅新建临时合成实例及模型替身；未操作正式实例、未调用真实模型。本次不是PF07的正式三次计时或规模验收。

## 结论

集中读取已经减少实际查询，但整根来源图缓存在这个完整样例中**一次也没有命中**。它进行了约482MB的累计编码准备，占用了接近4MiB的阶段缓存，却没有避免任何完整根图计算。应先消除这部分无收益工作，或把复用对象改成不同根真正共有的来源材料，而不是继续增加缓存额度。

带观察工具的总耗时162.868秒，Engine窗口162.841秒，来源检查互斥耗时151.233秒。这个数字包含SQL摘要、每次计数与方法计时的额外成本，不能与旧无观测137.928秒直接当作正式速度对照，也不能凭此声称优化已达PF03门槛。

事实命中率约87.34%，是实际收益。`facts_sql_reads`不包含checkpoint使用的PRAGMA、其它业务SQL或控制库SQL；全窗口SQL为1,293,259条。

图键包含实例、完整token、完整Scope和原节点／行上限，没有把剩余预算放进键。零命中不能归因于“预算参数每次变化”。实际调用中同一只读阶段通常有77个不同根；相同根出现在其它安全阶段／写事务代次时，又必须重新建立资料视图。这说明**完整根图不等于共同上游材料**。不同记忆、关系和目标可以有不同的根，却共享一段上游内容，当前整根缓存无法利用这种交集。

保留了1,265份图，不代表产生1,265次复用。360次“too_large”表示当时4MiB预算剩余空间不足，并非每份图单独都超过4MiB。

## 校验和跟踪成本

| 方法／观测 | 次数／数量 | 方法累计包含秒数 |
| --- | ---: | ---: |
| checkpoint | 4,629次 | 8.503 |
| checkpoint内文件签名访问 | 2,575,477项 | 已包含在checkpoint中 |
| track_artifact | 357,348次 | 10.435 |
| track_location | 385,409次 | 5.951 |
| 固定事实read方法 | 1,797,492次 | 14.623 |
| graph查找 | 1,625次 | 0.004 |
| remember_graph写入方法 | 1,625次 | 0.028 |

上述方法互相嵌套，也包含于阶段时间，**不能相加**。尤其`remember_graph`的0.028秒不包含调用方事先执行的`dumps(result)`；不能据此认为约482MB图序列化没有成本。`read`返回生成器时，后续遍历生成器的成本也不全在方法返回时间内。

checkpoint确实重复访问了大量签名，但其8.503秒不是当前151秒来源检查的全部解释。不应为了消除这8秒而跳过需要的篡改、外部提交或停止检查。

实际峰值：跟踪799个工件，缓存编码4,192,886／4,194,304字节，1,529个事实键＋53个图键，共1,582键。**先碰到的是编码空间，不是4,096键上限。** Python容器本身的额外内存不在该编码字节中。

保留材料的代次清理686次，全清理14次。事务代次清空可以解释整根图难以跨登记操作复用，但不能删除需要的写入失效规则来人为制造命中。

## 建议下一步

1. 首先避免对“第一次出现且本代次没有重复消费者”的整根图做昂贵序列化；也可移除这类零收益缓存。不要把它完成编码误报成共享来源成功。
2. 若继续来源图层优化，围绕已授权范围中的共同节点／依赖材料组织，保留各根自己的完整路径、Scope、版本、read/delete语义、逻辑扫描扣减及当前许可判断。先用本样例中确实共用一句话的多个不同根证明有命中，再进入正式速度比较。
3. 登记阶段仍占大头。只读事务清理和有写事务失效必须区别证明，不能依赖在事务内已被更新的`phase.changes`推断事务从未写入。
4. 文件跟踪与checkpoint成本有证据，现阶段先保留保护。后续若把核验集中到整个可信只读阶段，需要证明期间没有任意回调／写入，并在任何输出与保存前验证整个阶段一致；不直接删root检查。

本次没有改产品；仅扩充观察器和测试。三项观察器测试通过，包括互斥耗时守恒、异常恢复及SQL参数区分、事实／图命中与空间不足分类保持原结果。
