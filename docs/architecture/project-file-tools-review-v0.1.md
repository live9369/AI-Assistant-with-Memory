# 项目文件工具能力检查与接入建议 V0.1

日期：2026-11-15。状态：现状已检查，基础执行已验证；项目源码修改能力待实现。本轮仅调研、验证和设计，没有修改正式权限、唤醒配置或正式源码执行策略。

## 一、当前结论

已有真实工具执行链路，但尚不能完成项目源码修改任务。

| 能力 | 当前状态 |
|---|---|
| 提出工具动作、审批、执行、保存回执 | 已有 |
| 列目录、读文件 | 已有，仅限实例 workspace；读取上限 64 KiB |
| 创建文件 | write_note 已有；文件已存在但内容不同时拒绝覆盖 |
| 编辑、补丁、重命名、删除 | 未提供 |
| 执行命令、运行测试 | 未提供给原初00 |
| 修改项目根目录源码 | 不可；授权和 worker 都固定为实例 workspace |
| 读文件后继续推理再编辑 | 有 TaskLoop 基础，但按活动显式配置，上限 3 轮，验收仅支持 file_contains；正式库未发现该配置 |
| 自修改后部署 | 已有部署/回退基础，不等于已提供模型可用的开发与发布接口 |

正式实例只读检查：policy.mode=authorization；工具表仅 write_note/read_file/list_files；历史 action_intents 中存在 2 次成功 read_file。这个历史统计不是本轮真实模型调用证明。

## 二、本轮最小验证

在 TemporaryDirectory 中准备测试数据库，使用替身模型提出 write_note，然后经 Policy.approve 和 Engine.execute 启动真正的 worker 子进程。审批前文件不存在，执行后正文一致，action=succeeded、activity=completed。

没有替换工具后端，没有调用真实模型，没有修改正式实例。证据：`outputs/project-tools-review/existing-tool-probe.json`。这证明已有执行器可用，不证明当前真实模型一定会正确规划源码修改。

## 三、Codex 接入为何不能直接改文件

`digital_life/infrastructure/llm/codex_cli.py` 明确使用临时目录、ephemeral、read-only，关闭 shell 等工具，并拒绝输出事件中的工具调用。其职责是输出结构化行动候选。

这与“每次思考独立调用”的设计一致。建议保持这一职责，工具由数字生命自己的执行器调度。否则 Codex 在推理期间直接改文件，会绕开当前行为、审批、结果与记忆链路。

## 五、适合本系统的最小架构

请求 → 组装明确目标和项目范围 → 独立思考 → 工具意图 → 当前账户/目录/动作授权 → 文件或命令执行器 → 真实回执与文件差异 → 下一次独立思考 → 完成或继续。

下一轮显式携带本任务已读内容、修改差异和执行回执，不恢复或续用 Codex 内部会话。工具失败属于下一轮实际输入，不能仅靠模型说“完成了”。

### 1. 分清三个位置

- 项目源码：`<PROJECT_ROOT>` 中的源码、文档等；按目录明确可写范围。
- 实例运行数据：`work/primordial00-first-wake`，包括身份、数据库、记忆、授权、发布快照。应通过已有专用服务修改，不纳入一般源码编辑工具。
- 已部署版本：`work/.../releases`。源码编辑不立即替换已加载程序；发布仍经 CLI 和已有部署/回退链路。

开发候选目录是代码版本，不是另一个生命实例。已有身份和记忆始终属于原实例。

### 2. 第一版工具

- project_list / project_search：定位相关文件；项目已索引时优先接 CodeGraph，文本搜索作为补充。
- project_read：按行分页，返回内容、文件版本 hash 和实际路径；避免只因文件超过 64 KiB 就无法读源码。
- project_patch：新建和修改文本文件，携带预期旧 hash；文件已被他人改动则返回冲突，由下一次思考重新读取。多文件先全部核对，再提交；中途异常有恢复日志和修改前副本，不能声称文件系统天然跨文件原子。
- project_diff：显示实际修改及版本，不依赖模型的文字总结。
- project_check：第一版运行具名检查项，指定程序、参数、工作目录、超时、输出上限；后续再扩展通用 exec 与进程管理。

目前仓库没有可用 .git。不能假定 worktree 已可用；第一版可复用版本快照，是否引入 Git 单独配置。不得为了设计示例擅自初始化或改写历史。

### 3. 授权与执行

沿用 root 才能提出系统动作的账户边界。授权模式和自动允许模式继续作为配置选择：可对已明确授权的源码目录自动执行，不必每次重复确认。同一个账户角色不能自动推出“已获全部文件或部署权限”。

新增资源类型 project-files，不再把全部 grant/root 硬编码为实例 workspace。工具参数、文件范围、权限代次必须与审批时一致，执行前再次核对。

路径校验落实到实际执行，处理绝对路径、符号链接及检查后被替换的情况。仅设置 cwd 并不能约束 shell；若开放通用命令，需要独立 OS 沙箱/容器或明确接受宿主权限范围，不能把字符串命令白名单声称为完整隔离。

### 4. 文件任务循环

复用并扩展 TaskLoop：读取 → 修改 → 读回/具名检查 → 修正或结束。让任务配置能从聊天请求进入，不能要求用户先手工给每个 activity 写配置。

每轮仍独立调用。轮数、工具次数和总耗时从任务预算控制；不在本轮擅自提高预算。接近预算时保留变更和结果，报告未完成项，避免无边界探索。

### 5. 自修改与生效分开

先允许它阅读并修改开发代码；修改当前源文件不等于当前进程已更新。完成后产生可审查差异和检查结果，交给既有 CLI 发布，保留上一部署。第一版不让源码编辑工具顺带覆盖部署、控制数据库或回退机制。

这延续原定的“允许修改源码、版本管理、失败回退、部署启动唤醒由 CLI 处理”。它是否能够编写有效实现，需要实际任务验证，不能仅凭工具存在认定。

## 六、实施顺序与最小验收

1. 项目资源和授权字段：明确可读/可写目录、动作、版本与日志映射。
2. 项目定位、分页读取、带旧版本校验的 patch 和 diff：先打通修改已有文件。
3. 聊天到文件任务循环：工具回执进入后续独立调用；只针对本任务收束。
4. 具名运行检查和修改记录：证明改动实际产生并执行，失败保留依据。
5. 现有 CLI 发布接口衔接：源码版本、部署版本、身份数据分别核对，验证失败保留旧部署。

仅做核心验收：新建并读回一个文件；修改一个已有文件并查看 diff；文件被外部修改时拒绝旧补丁；授权目录之外不写入；运行一次具名检查；完整任务结束时能解释真实结果。完成工具接入后再做一次真实模型任务验收。本轮不扩展长期自主开发测试。
